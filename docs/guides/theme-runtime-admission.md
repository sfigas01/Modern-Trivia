# Themed game admission (STE-25 / STE-167 S11A)

Themed rooms require a signed-in host. Room creation and category suggestions check a real sign-in session; themed Start requires that session plus the host player token, and the session account must match the account stored on the room's host. Scripted admin API credentials do not qualify as player sign-in. Guests may join with a stable opaque browser subject. All themed games use five rounds, with 40/60/80 questions for 2/3/4 players.

Start locks the room, snapshots the roster, creates one durable game and preparation job, records the immutable generation owner account, and persists the room's preparation reference in one PostgreSQL transaction. Repeated Start requests return the same game/job after committing and releasing the admission connection, so retries also work with a bounded connection pool. Admission uses identities already persisted at creation/join and locks their history union in sorted order, so opposite seat orders across rooms do not invert account locks. A partial unique index additionally prevents two live games for one room. Join, leave, and automatic host changes respect the preparation lock. The host can end preparation, which cancels the job and releases reservations in the same room transaction.

Each browser stores a random subject UUID in local storage. The server stores only a hash, resolves authenticated account identities from the session, and links the browser's guest history when it signs in. The locked roster contains distinct multiplayer history identities. Shared-device multi-seat admission is deferred: there is no shared-device runtime adapter in this slice, and duplicate history identities are explicitly rejected by the multiplayer adapter. Future shared-device support must separate seats from deduplicated history subjects rather than inventing a subject for every seat.

Backup selection excludes the union of every locked participant's history: questions and canonical facts displayed within the last 30 days **or** within each identity's last five games with actual displayed questions. Linked browser/account subjects are included. Recent legacy `seen_questions` contributes exact IDs and any mapped canonical facts; the legacy table cannot reconstruct game boundaries, so last-five protection applies to durable exposure records only. Current guest `guest_seen_ids` adds conservative exact-question exclusions. Account history is server authoritative.

The full 40/60/80-question related backup set must be available before any generation. Every backup requires an exact S10 approval, library question revision, canonical fact revision, and current passing S8 evidence graph under the configured policy. Ordinary approved questions without that provenance are excluded. Mutable library content must still match its approved snapshot. Locks and per-identity/fact reservation uniqueness prevent overlapping games from holding the same fact. Incomplete inventory persists a durable `related_inventory_shortfall` and holds no partial backup set. Reservations do not count as ready questions or exposure.

S11A is dormant: it dispatches no provider, Guardian, embedding, legacy preparation, or background worker call, and never activates a room. Category suggestions use the deterministic keyword fallback. The production route has no live evidence-policy/prompt configuration yet; that fails closed as an explicit inventory shortfall. S11B must compose the authoritative policy with the worker before preparation can run. Daily/weekly account and global monetary caps are a separate S11B admission/dispatch requirement, before any paid provider is enabled.

`recordThemeExposure` is a transaction-only server helper for the later activation adapter. It accepts only a selected/displayed reservation for an active game and locked participant, locks history subjects, and records an idempotent display key. Held backups never write exposure. There is no client endpoint that can invent theme exposure.

Migration `0017_theme_runtime_admission.sql` adds room/job linkage, player identity linkage, immutable owner binding, and the active-room/account uniqueness guards. The room preparation reference has a restrictive foreign key; deleting an expired room leaves its durable game/history intact. Existing schema columns and constraints remain additive.

Validation includes route tests for session and participant authorization, deterministic suggestions, five-round enforcement, and roster locks; unit tests for full backups, atomic rollback, explicit shortfall, history union, stable identity linking, and exposure guards; and opt-in PostgreSQL tests for competing Starts, durable ownership, uniqueness, and history windows. Run PostgreSQL tests only with a disposable `THEME_RELIABILITY_MIGRATION_TEST_DATABASE_URL`; application/production `DATABASE_URL` is never substituted.

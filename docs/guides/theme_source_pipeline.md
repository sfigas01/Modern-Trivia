# Theme evidence eligibility policy kernel

`server/lib/theme-evidence-eligibility.ts` makes a synchronous, deterministic decision over a complete caller-supplied graph: the live question snapshot, its immutable revision, all reviews for that revision, reviewed fact revisions, cited passages and documents, and fact-to-passage bindings. It performs no retrieval, database access, model call, or factual judgment. This is an S1 policy slice; no route or generation flow calls it yet.

The caller injects `now` and an explicit policy containing current source, extractor, review, and prompt versions; allowed source classes; maximum document and review ages; and the minimum number of independent origin groups **per reviewed fact**. Null expiry means the relevant age limit still applies. Expiry is exclusive: evidence is stale at its `validUntil` timestamp.

Question content hashes use SHA-256 of the complete `QuestionContentSnapshot`, serialized as JSON with object keys sorted recursively and array order preserved. `hashQuestionSnapshot` exposes that encoding for future writers. Eligibility requires the live snapshot, live content hash, revision snapshot, revision content hash, and selected review binding to agree exactly. A content change needs a new revision and review.

All supplied reviews are structurally checked before selection, so a malformed later row cannot expose an older pass. For the exact revision, the latest review sorts by descending `reviewedAt`, then descending review UUID for a stable timestamp tie. A newer adverse review, wrong policy version, or expired review withholds; the evaluator does not fall back to an older pass. Every one of the seven review dimensions must pass and cite a passage bound to a reviewed fact with a supporting edge. Any conflict edge for a reviewed fact withholds even if that passage was omitted from the review citations. Each cited passage must resolve to a current, allowed document, and every reviewed fact must have enough distinct supporting `originGroup` values among its citations.

The reviewed fact must also be the latest supplied revision of its fact identity. At least one reviewed fact's canonical answer must equal the question answer. Every accepted answer must be that answer or a supported alias on an answer-bearing fact; a separate contextual fact cannot expand the accepted-answer set. The source adapter must supply the full revision and conflict set for these checks; an incomplete graph cannot establish eligibility.

The decision returns a typed reason and a `theme-eligibility-v1` fingerprint. The fingerprint hashes the validated graph and policy in stable ID order, so evidence or policy mutation invalidates a prior decision without depending on database row order. It does not grant lasting authorization: a caller must reevaluate with the current time and graph before activation or reservation. The kernel cannot verify the bytes behind a document's stored hash or establish that a passage actually entails a claim; those require source retrieval, independent review, and evaluation work outside this slice.

## S2a source registry and provenance

`shared/models/theme-source-registry.ts` defines the strict `theme-source-registry-v1` manifest. Each version contains 1–200 immutable entries with a stable ID, publisher identity and origin group, source class, lightweight scope metadata, and exact HTTPS origins and path rules. Empty topic and geography lists mean broad coverage, and a null temporal range means the registry does not narrow the source by date. This lets a broadly useful reference such as Wikipedia be approved once instead of curated theme by theme. Each entry permits 1–20 origins and at most 50 paths total. Path rules are exact or subtree (ending in `/`); wildcards, regular expressions, query strings, fragments, credentials, unsafe encoded paths, and non-HTTPS origins are rejected. Cross-entry overlapping rules are rejected because a URL must identify exactly one source. The resolver returns `matched`, `missing`, `invalid_url`, `not_allowed`, or `ambiguous`.

The server canonicalizes entries, origins, paths, and scope sets before hashing the complete manifest with SHA-256. `theme_source_registry_versions` stores the full canonical manifest and hash by `sourcePolicyVersion`; a repeated append of the same version and content is idempotent, while a changed manifest under the same version is an error. Reads validate the schema and recompute the hash. Migration `0010_theme_source_registry.sql` makes registry versions append-only.

`theme_evidence_document_sources` binds a document to the exact registry version, hash, and entry. Binding runs in a transaction and checks the document's stored policy version, publisher ID/name, origin group, source class, and requested/final/canonical URLs against that entry. The database additionally checks the registry reference and provenance metadata on sidecar insertion; its immutable trigger prevents changing or deleting a binding. URL rule resolution and the SHA-256 manifest check are application validations, so direct database writers must use the repository to receive those checks.

Existing `0009` evidence documents are intentionally unbound. Migration `0010` adds no global constraint requiring every future document to have a sidecar, because existing insertion paths have not been migrated. A document without a verified sidecar has no registry provenance claim; later retrieval and eligibility integration must enforce binding at their own boundary. This slice does not retrieve, extract, review, or use a document for a game.

The registry says which source locations the pipeline may use; it does not declare every statement on a page true. Wikipedia is suitable as a broad secondary reference for ordinary stable facts, aliases, dates, and scope. The later evidence policy can require stronger or additional support for disputed, rapidly changing, or superlative claims without making the registry itself a large editorial workflow.

## S2b bounded source retrieval

`server/lib/theme-source-retrieval.ts` retrieves a URL against an exact stored registry version and records its registry hash, matched entry, publisher, origin group, source class, redirect chain, retrieval policy version, timestamp, and SHA-256 hash of the exact response bytes. This is an isolated library; no generation, review, route, or game flow calls it yet. The caller supplies a registry reader, with DNS, transport, and clock injection available for deterministic tests. There is no production source seed or per-theme source list. A registry entry can allow a broad reference path such as Wikipedia's `/wiki/` across ordinary themes.

Each request and redirect must resolve to the same registry entry. The retriever accepts at most three redirects, rejects loops, validates every A and AAAA answer as public before selecting one, and pins that address for the HTTPS connection while retaining the hostname for Host, SNI, and certificate validation. IPv6 validation conservatively rejects IANA special-purpose allocations, including allocations that may be globally reachable, because the retriever only needs ordinary public publisher addresses. It verifies the peer address and never uses a shared agent or proxy. One ten-second deadline covers the whole retrieval; connection/TLS and inactivity limits are three and two seconds. Headers are limited to 16 KiB and response bodies to 2 MiB. Successful input is a complete, nonempty HTTP 200 `text/html` or `text/plain` response with identity encoding. Failures use the existing `RetrievalFailure` codes and safe fields. This stage does not extract passages or make factual judgments.

## S3 deterministic passage extraction

`server/lib/theme-source-extraction.ts` synchronously converts a `RetrievedThemeSource` into passage candidates for the existing passage contract (without database IDs or `documentId`). It has no network, model, database, or clock dependency and is not wired to generation or gameplay. The extractor version is `theme-source-extractor-v1`; changing normalization, selection, exclusions, or locator behavior requires a new version and re-extraction before evidence can be reused.

Retrieval preserves a normalized nullable `charset` from `Content-Type`: missing charset becomes `null`, and UTF-8 aliases become `utf-8`. Other, malformed, duplicate, or conflicting charset declarations fail retrieval. Extraction rechecks the exact response-byte SHA-256 hash, enforces the 2 MiB input bound, and decodes UTF-8 fatally before parsing. An absent charset is interpreted as UTF-8; invalid UTF-8 still fails. HTML `meta charset` and `http-equiv="Content-Type"` declarations must also specify supported UTF-8; malformed or conflicting declarations withhold the whole extraction even when the HTTP charset was absent. Decoded control characters other than tab and line breaks, plus Unicode noncharacters, are rejected for both HTML and plain text. No fallback decoding or replacement characters are permitted.

HTML uses a direct `parse5` production dependency. Material parser corruption, including unexpected null characters and truncated tags, withholds the whole extraction; ordinary missing doctypes and optional end tags remain acceptable. The extractor chooses the first visible `main`, otherwise `article`, otherwise `body`; there are no publisher or hostname branches. It takes visible headings, paragraphs, and list items in document order. Nested block boundaries become spaces within a candidate, while inline text remains joined. Scripts, styles, templates, noscript, navigation, asides, footers, headers, forms, embedded content, hidden elements, non-prose landmarks, a narrow set of known table-of-contents/page-chrome classes and IDs, and all tables are excluded. A candidate containing visible MathML or non-reference superscript/subscript notation is withheld rather than flattened; ordinary reference superscripts are removed as citation chrome while retaining the surrounding prose. Plain text is split on blank lines. Unicode NFC and whitespace normalization produce the exact stored passage text; SHA-256 hashes that text as UTF-8. Duplicate normalized text is retained once at its first structural locator, with dense zero-based ordinals. HTML locators use structural element paths and a path hash when the path would exceed the 500-character contract limit; plain-text locators identify paragraph positions.

The entire extraction fails with a typed reason for changed bytes, unsupported charset, invalid UTF-8, no prose, or a resource limit. Limits are 12,000 characters per passage, 500,000 extracted candidate characters, 100,000 parsed nodes, depth 256, and 10,000 candidates. A limit never yields a partial passage set. These are extraction candidates, not verified facts: downstream work must still judge provenance, scope, claim support, ambiguity, and freshness before approving a question.

## S4 evidence capture persistence

`server/lib/theme-evidence-persistence.ts` accepts a caller-chosen stable document UUID, one successful retrieval, its successful S3 extraction, and explicit title and language. The caller may use `und` when the language is unknown. The adapter snapshots and re-extracts the response bytes before connecting to PostgreSQL, then requires the entire ordered passage set, extractor version, locators, exact text, and hashes to agree. Existing document and passage schemas validate the projection, and PostgreSQL-unsafe strings are rejected before any write.

One transaction inserts the `theme_evidence_documents` row, exact registry version/hash/entry sidecar in `theme_evidence_document_sources`, and every `theme_evidence_passages` row. The registry check resolves the requested URL, final URL, canonical URL, and all recorded redirect hops to the same entry. The document records the retrieval byte hash, timestamp, HTTP status, media type, publisher identity and source class, source policy version, extractor version, title, and language. Its canonical URL is the retrieval's final URL; status is `retrieved`; published, source-updated, and expiry timestamps are null until another verified process can establish them. Each passage stores its ordinal, structural locator, exact normalized text, and text hash.

A repeated call with the same UUID succeeds only when the stored document projection, registry binding, and complete ordered passages match. It returns the original passage IDs. A changed or incomplete capture returns `capture_conflict` and is never repaired in place. Different UUIDs may intentionally retain identical URLs or response bodies as separate captures. Failures before commit roll back the entire capture; an uncertain commit result reports `storage_unknown_outcome`, so callers can retry with the same UUID. This is an isolated repository library and is not wired to routes, generation, review, or gameplay.

The current schema does **not** archive raw response bytes, redirect hops, charset, or retrieval policy version. The stored rows therefore prove the persisted metadata, registry binding, and extracted text, but do not preserve the complete retrieval envelope for later byte-level re-extraction. Callers that need that audit capability must store the envelope separately in a future slice.

## S5 scoped fact proposals

`server/lib/theme-fact-derivation.ts` accepts a caller-chosen canonical fact key and revision UUID, an expected latest revision, an explicit source and freshness policy, an injected clock, and the exact passage IDs to consider. It lowercases validated UUIDs before duplicate checks, lookup, citation matching, and replay. It loads at most 12 passages and 32,000 passage characters. Every passage must have its exact stored text hash, a current retrieved HTTP 200 document, an unexpired source within the policy's maximum age, and a valid sidecar bound to the exact registry manifest hash and entry. The document's publisher, origin group, source class, and requested/final/canonical URLs must match the registry, and its language must be explicitly listed in the matched entry's language scope. Missing or invalid evidence fails closed before the proposer runs.

The injected proposer receives only passage IDs, text, and hashes. It returns `insufficient_evidence`, `conflicted`, or one `proposed` fact with a statement, complete fact scope, canonical answer, aliases, time sensitivity, and unique passage citations marked `supports`, `conflicts`, or `context`. It cannot assign database IDs, revision numbers, content hashes, publisher identity, origin groups, expiry, or approval. A proposal needs at least one supporting passage; an explicit conflict withholds it. `supportOriginCount` counts distinct registry origin groups among support citations. Wikipedia is an ordinary `secondary_reputable` source and contributes at most one group. A proposed result below the configured minimum has `policySatisfied: false` and is not persisted.

The immutable fact hash is SHA-256 of UTF-8 canonical JSON for `{statement, scope, canonicalAnswer, supportedAliases, timeSensitive, validUntil}`. Canonical JSON sorts object keys recursively and preserves array order; aliases are first normalized to Unicode NFC, deduplicated, and sorted by code-point order. The fact's scope comes from the existing strict scope schema. Time-sensitive proposals require an `asOf` no later than the current time and no later than at least one supporting document retrieval. Their expiry is `asOf + policy TTL`, capped by the earliest expiry among supporting documents. This keeps expiry and hash stable on retry instead of refreshing the TTL. Other proposals inherit the earliest supporting document expiry, if any.

After proposal generation, the writer starts one transaction, locks the canonical fact identity, reloads the exact evidence against the current clock and policy, verifies it has not changed, checks the expected latest revision, and inserts the revision with its complete passage bindings. A completed derivation attempt replays its stored result without running the proposer again; a revision that already exists outside that attempt cannot be retroactively bound to it. An attempt to write the same semantic hash with different evidence returns `evidence_change_conflict`; it needs a changed fact snapshot or a later policy design, since the current schema forbids duplicate hashes per fact. A failed write rolls back, and an uncertain commit discards the database connection and reports `storage_unknown_outcome` so the same attempt UUID can be inspected on retry.

These rows record a **proposal**, not factual entailment, independent review, question approval, or gameplay eligibility. The proposer is injected; this slice makes no model call and is not wired to routes or jobs.

## S6b independent fact review

`server/lib/theme-fact-review.ts` adds an injected, model-agnostic review boundary. Trusted configuration fixes the reviewer identity, execution metadata, policy snapshot, prompt version/hash, and review validity period. The repository loads only a fact revision bound to a persisted S6a derivation outcome, checks that the fact snapshot and its complete cited-edge set still match, and reconstructs every passage from the S6a input manifest. The reviewer receives all originally offered passages, including uncited material, so contradictory evidence cannot be hidden by the proposer’s citations. Evidence remains bounded to 12 passages and 32,000 characters and is rechecked for hash, provenance, policy, and freshness before a terminal outcome is stored.

Review output has exactly six strict dimensions: entailment, scope, canonical answer, aliases, conflict, and source independence. Each dimension supplies a bounded verdict, allowlisted reason codes, and unique exact passage ID/hash references. The repository computes the aggregate verdict; a reviewer cannot choose it. `no_aliases` is valid only when the fact has no aliases. Reviewer identity, execution UUID, and model provider/model pair must be independent from the derivation producer. The immutable attempt header commits before the callback runs. Exact completed replay returns the stored outcome; a changed attempt conflicts and an unresolved header never triggers automatic redispatch. Invalid output and callback failure store allowlisted codes only.

`server/lib/theme-fact-review-eligibility.ts` deterministically chooses the highest review sequence for the exact current revision before considering its result. A newer pending, failed, flagged, failed-verdict, expired, or mismatched review blocks an older pass. Eligibility also requires unchanged derivation and evidence fingerprints, complete provenance, sufficient independent supporting origins, no conflict edge, and current fact/review freshness. This authorizes fact candidacy only; it does not approve questions or gameplay.

## S6a immutable derivation provenance

Every new call to the fact writer supplies a trusted attempt UUID, execution UUID, derivation policy version, prompt version and template text, and producer identity. A model producer also supplies provider and model identifiers; a human producer leaves those null. The proposer cannot assign these values. The writer validates all fields, hashes the prompt text without storing it, and constructs a bounded input manifest from the exact request and ordered passage hashes, document metadata, and registry sidecars. No raw passage or prompt text goes into the manifest. SHA-256 hashes use the canonical JSON form described above, except the prompt hash, which covers its exact UTF-8 bytes.

After evidence preflight, `theme_fact_derivation_attempts` commits this immutable header before the proposer runs. A completed attempt with the same exact header returns its stored result without redispatch. A changed header returns `attempt_conflict`; a header without an outcome returns `attempt_unresolved` and is never automatically redispatched. The separate immutable outcome records `persisted`, `insufficient_evidence`, `conflicted`, `policy_unsatisfied`, `invalid_output`, or `failed`. Invalid output and proposer failures retain only safe failure codes, never raw output. A successful fact revision, all its passage bindings, and its persisted outcome commit together; composite foreign keys bind the outcome to the attempt's requested revision ID and the revision's exact content hash. Each revision can be claimed by only one outcome, and the binding fingerprint commits to sorted citation IDs, passage hashes, and support kinds. Existing revisions remain valid legacy rows without derivation provenance, and this repository no longer creates new ones. These records are audit provenance, not independent factual review or gameplay eligibility.
